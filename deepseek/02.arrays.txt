Bro, this is a **Prefix Sum template**. Its whole purpose is:

> **Pre-calculate cumulative sums so that any subarray/range sum can be answered in O(1).**

### Without Prefix Sum ❌

Suppose:

```text
nums = [2, 4, 1, 5, 3]
```

Question:

```text
sum(1, 3)
```

means:

```text
4 + 1 + 5 = 10
```

If you calculate every query by looping:

```java
for (int i = L; i <= R; i++) {
    sum += nums[i];
}
```

that's **O(N) per query**.

If there are 100,000 queries → potentially very slow.

---

### Prefix Sum ✅

Your constructor builds:

```text
nums:    [2, 4, 1, 5, 3]

prefix:
         [0, 2, 6, 7, 12, 15]
          ↑
        empty
```

Meaning:

```text
prefix[0] = 0
prefix[1] = 2          = 2
prefix[2] = 6          = 2 + 4
prefix[3] = 7          = 2 + 4 + 1
prefix[4] = 12         = 2 + 4 + 1 + 5
prefix[5] = 15         = total
```

Now ask:

```java
query(1, 3)
```

Your code:

```java
prefix[R + 1] - prefix[L]
```

becomes:

```text
prefix[4] - prefix[1]

12 - 2

= 10
```

Why?

```text
prefix[4] = 2 + 4 + 1 + 5
prefix[1] = 2

Remove the unwanted 2:

(2 + 4 + 1 + 5) - 2
= 4 + 1 + 5
= 10
```

### 🔥 The interview AHA

Think:

```text
PREFIX = sum from beginning

RANGE SUM = PREFIX AFTER R - PREFIX BEFORE L
```

So:

```text
sum(L...R)
      ↓
prefix[R+1] - prefix[L]
```

### Complexity

| Operation        | Complexity |
| ---------------- | ---------: |
| Build prefix     |       O(N) |
| Each range query |   **O(1)** |
| Extra space      |       O(N) |

So if the interviewer says:

> "Given an array, answer many queries asking for the sum between L and R."

Your brain should immediately say:

**"Prefix Sum."** 🧠

This is one of those templates you should **recognize**, not spend a huge amount of time studying.

Yes bro — **we did Top K Frequent with a heap too.** And this is a very important distinction for interviews.

You have **two valid patterns** for LC 347:

### 1️⃣ HashMap + Min Heap — what you remember

```text
frequency map
     ↓
min-heap ordered by frequency
     ↓
keep only K elements
     ↓
top K
```

The key AHA:

> We use a **min-heap of size K** because the smallest frequency among our current top-K should be the first one removed.

Complexity:

```text
Build frequency → O(N)

For M unique elements:
heap → O(M log K)

Total → O(N + M log K)
≈ O(N log K)
```

This is generally the **safer interview solution** because it works without assuming a bounded frequency range.

---

### 2️⃣ Bucket Sort — your HTML template

```text
frequency map
      ↓
bucket[frequency]
      ↓
start from highest frequency
      ↓
collect K
```

Example:

```text
[1,1,1,2,2,3]

frequency:

1 → 3
2 → 2
3 → 1
```

Buckets:

```text
bucket[3] → [1]
bucket[2] → [2]
bucket[1] → [3]
```

Walk backward:

```text
3 → 1 ✅
2 → 2 ✅
```

Answer:

```text
[1,2]
```

Complexity:

```text
Frequency map → O(N)
Build buckets  → O(M)
Scan buckets   → O(N)
----------------------
Total          → O(N)
```

---

### 🧠 What I want you to remember for Roku

Don't memorize both implementations equally.

Remember the **decision**:

```text
Top K?
   ↓
Need straightforward / flexible?
   → Min Heap O(N log K)

Need O(N) and frequency is bounded by N?
   → Bucket Sort
```

And importantly, **your statement "min heap remove all mins so we have max sorted" is slightly imprecise.**

The heap isn't sorting everything.

It's maintaining:

```text
ONLY the best K candidates
```

That's the AHA.

For example K = 2:

```text
heap = [frequency 2, frequency 3]
             ↑
        weakest of top K
```

If a frequency 5 arrives:

```text
remove frequency 2
add frequency 5
```

So the heap stays size 2.

That's why we get **O(N log K)** instead of sorting all unique elements.

Your **Top K pattern is already covered**. We don't need to reteach the problem—just make sure you can recognize **Heap vs Bucket** quickly.
